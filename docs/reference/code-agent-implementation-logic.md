## 1. 最重要的结论

一个代码智能体（Code Agent）的核心不是“让模型会写代码”，而是把模型放进一个受控的任务运行时（Runtime）里，让它在真实工程环境中持续完成这条闭环：

```text
理解目标
  -> 组装上下文
  -> 选择动作
  -> 检查权限
  -> 执行工具
  -> 接收观察
  -> 更新状态
  -> 验证结果
  -> 决定继续、暂停、回退、压缩、重规划或结束
```

如果把整套设计压成一句话，就是：

```text
代码智能体（Code Agent）= 模型（Model）+ 运行时（Runtime）+ 工具（Tools）+ 上下文（Context）+ 状态（State）+ 策略（Policy）+ 评测（Eval）
```

模型只是决策者之一，不是系统本身。真正让它从“聊天助手”变成“代码任务运行时”的，是模型外面的这些结构：

| 对象 | 它解决什么问题 |
| --- | --- |
| 会话（Session） | 一次任务的持续状态、恢复和审计边界 |
| 消息流（MessageStream） | 用户消息、模型输出、工具结果和运行时事件的事实流 |
| 上下文引擎（ContextEngine） | 决定本轮模型能看见哪些事实 |
| 模型网关（ModelGateway） | 解析、校验、预算控制和模型服务商适配 |
| 工具运行时（ToolRuntime） | 执行搜索、读取、编辑、命令等真实动作 |
| 策略与权限（Policy / Permission） | 判断动作允许、询问还是拒绝 |
| 计划状态（PlanState） | 把计划从文本变成可审批、可恢复的状态机 |
| 压缩（Compaction） | 在上下文压力下保住任务关键状态 |
| 评测证据（EvalEvidence） | 证明机制是否真的成立，并归因失败 |
| 边界契约（BoundaryContract） | 说明能声称什么，不能声称什么 |

早期文章讲清楚了一个判断：AI 编程（AI Coding）的中心会从“帮助人写代码”迁移到“帮助系统持续推进软件任务”。现在完整课程和 Core 01-31 补上的，是这句话的工程版本：

```text
要持续推进软件任务，就必须把每一次模型判断、工具行动、环境反馈和能力声明都落成运行时对象，并且能被验证脚本复现。
```

## 3. 不要从功能列表开始，要从主对象开始

如果只看功能，一个代码智能体看起来很简单：

```text
读文件
搜代码
改文件
跑测试
做计划
总结结果
```

但这些只是表面。真正的问题是：

```text
这些功能被谁组织？
谁记录事实？
谁决定模型这一轮看见什么？
谁阻止危险动作？
谁判断完成是真的完成，而不是模型自己说完成？
```

所以搭建代码智能体的第一步，不是先写一个“问模型”的函数，也不是先堆工具，而是先确定系统主对象。

本项目的主对象链是：

```text
用户目标
  -> 会话
  -> 消息流
  -> 上下文引擎
  -> 模型网关
  -> 工具运行时
  -> 策略与权限
  -> 状态更新
  -> 验证证据
  -> 下一轮
```

这也是为什么本项目不从一个完整智能体一步写起，而是先从 Course 00 到 Course 06 建立心智模型，再用 Lab 01-08 拆出最小机制，最后进入 Core 01-31。

正确顺序是：

```text
先定义对象
再定义对象之间的数据流
再定义每条边上的权限和失败语义
最后才让模型在这个运行时里做选择
```

## 4. 第一阶段：最小运行时循环

一个最小代码智能体闭环长这样：

```text
用户目标
  -> 追加用户消息
  -> 构造本轮上下文
  -> 暴露工具模式
  -> 调用模型
  -> 解析模型决策
  -> 检查权限
  -> 执行工具
  -> 追加工具结果
  -> 更新状态
  -> 验证结果
  -> 继续下一轮或结束
```

它看起来像普通循环，但语义完全不同。普通聊天系统是一问一答；代码智能体的循环必须把工具结果作为下一轮事实重新送回模型。

最小伪代码可以写成中文：

```text
只要会话还没有结束：
  上下文 = 上下文引擎根据会话构造本轮可见事实
  工具列表 = 工具运行时描述本轮可用行动
  模型决策 = 模型网关调用模型并解析输出

  如果模型给出最终回答：
    检查是否有验证状态或明确边界
    结束任务

  如果模型请求工具：
    权限结果 = 权限解析器判断允许、询问或拒绝
    工具结果 = 工具运行时执行或返回拒绝结果
    消息流追加工具结果
    状态存储应用工具结果

  如果上下文压力过高：
    压缩器保留关键任务状态
```

这里有五条不变量：

```text
模型不能直接读写文件，只能请求工具。
工具结果不能丢，必须进入消息流。
失败不是异常吞掉，而是观察。
最终回答不能凭模型感觉，必须被验证状态或边界说明支撑。
高风险动作不能靠提示词自觉，必须由运行时拦截。
```

Lab 01 和 Lab 02 证明了最低版本：工具结果（ToolResult）必须回灌到第二次模型请求（ModelRequest），消息流（MessageStream）必须追加式记录，并且孤立工具结果、重复工具结果都要被拒绝。

Core 01 把这条链集成为最小运行时：搜索（Search）、读取（Read）、编辑（Edit）、命令执行（Bash）、最终回答（FinalAnswer）都进入同一个事实流；编辑受“先读再写”、旧字符串唯一、文件未过期约束；命令验证结果进入状态；最终回答必须基于验证。

这就是代码智能体和“模型写一段补丁（patch）”的分水岭：

```text
智能体不是一次生成，而是状态驱动的执行闭环。
```

## 5. 消息流：系统的事实层

真正的智能体不是动作更多，而是反馈能更新下一轮认知。落到实现上，这个“认知更新”首先不是模型权重更新，而是下一轮可见事实更新。

消息流（MessageStream）就是这个事实层。

它记录：

```text
用户消息
模型消息
工具调用
工具结果
策略拒绝
验证结果
运行时事件
压缩摘要
人工批准事件
子任务委派事件
```

为什么这层重要？

如果搜索结果没有进入事实流，模型就只能猜文件；如果读取结果没有进入事实流，编辑就会变成凭空补丁；如果命令失败没有进入事实流，下一轮就不能从失败中恢复；如果权限拒绝没有进入事实流，模型就不知道应该换路径。

所以实现代码智能体时，要把所有外部反馈都转成结构化观察：

```text
文件不存在（file_not_found）
权限拒绝（permission_denied）
文件未读取（file_not_read）
文件已过期（stale_file）
命令失败（command_failed）
缺少验证（verification_missing）
需要批准（approval_required）
被钩子阻断（blocked_by_hook）
外部改动冲突（external_change_conflict）
重复研究复用（duplicate_reused）
```

这些不是界面文案，而是运行时状态语言。

一个成熟的代码智能体不应该让模型在原始日志里自己猜。它应该把关键反馈变成可挂载、可比较、可累积的事实对象。

## 6. 工具不是函数调用，而是受治理的行动能力

很多人会把工具理解成“模型可以调用的函数”。这太轻了。

在代码智能体里，工具是会改变世界的行动能力。读文件会暴露信息，编辑会改变工作区，命令会运行外部程序，测试会消耗时间并产生长输出。因此工具必须有协议、权限、状态和审计。

本项目从 Lab 03 到 Lab 04 建了最小工具层：

| 工具 | 运行时要求 |
| --- | --- |
| 搜索（Search） | 返回匹配文件和行，搜索不到也要返回成功观察 |
| 读取（Read） | 返回文件内容，并受路径安全约束 |
| 命令执行（Bash） | 只允许运行白名单命令，非零退出转成工具结果 |
| 编辑（Edit） | 必须先读取，旧字符串唯一，文件不能过期 |

Core 22 又把工具运行时推进到事务层：

```text
差异预览（diff preview）
多文件事务（multi-file transaction）
提交（commit）
回滚（rollback）
过期重读（stale reread）
受保护文件批准（protected file approval）
高风险命令路由（high-risk Bash routing）
```

到这里，编辑不再是“替换字符串”这么简单。它变成了一个受控交易：

```text
先证明你读过这个文件；
再证明你替换的是唯一片段；
再证明文件没有被外部改过；
再生成差异预览；
再按风险决定是否需要批准；
最后才写入；
失败时可以回滚。
```

这就是工具层的核心原则：

```text
模型提出意图，运行时执行动作。
模型不能因为“说服了自己”就越过工具协议。
```

## 7. 模型网关：模型可以换，但边界不能换

真正搭建智能体时，很容易把所有注意力放在模型上：换哪个模型、温度多少、提示词怎么写。

但工程上更关键的是：模型必须被接在一个稳定边界后面。

模型网关（ModelGateway）做四件事：

```text
调用模型服务商适配器（provider adapter）；
解析模型输出；
把输出归一成最终回答或工具调用；
在执行前校验工具名、必需输入、模式和能力面。
```

Core 02 的意义不是“接了一个模型接口”，而是证明：

```text
模型层可以替换，但运行时、工具、策略、消息存储边界不变。
```

Core 07 继续证明真实模型接口的本地契约：即使接入真实模型服务商边界，本地运行时仍然执行工具、保留评测证据，并且请求体不包含密钥。

Core 23 再往前推进一层：模型网关在模型服务商调用前就可以做预算和能力决策：

```text
词元预算闸门（token budget gate）
成本预算闸门（cost budget gate）
重试与降级（retry / fallback）
能力过滤（capability filtering）
输出修复（output repair）
不可重试失败分类（non-retryable failure classification）
```

这说明模型网关不是“发请求的薄包装”，而是模型调用的治理层。它决定：

```text
这轮请求是否应该发；
发给哪个模型服务商；
暴露哪些工具能力；
失败是否应该重试；
输出能否修复；
什么时候必须失败而不是硬凑。
```

所以实现顺序应该是：

```text
先把运行时边界建稳，再替换模型。
不要让模型服务商接口形状反过来污染运行时对象模型。
```

## 8. 上下文引擎：模型“知道什么”不是自然发生的

不要说“模型知道”。更准确的说法是：

```text
模型本轮能看见什么，取决于上下文引擎在这一轮把什么放进模型请求。
```

上下文引擎（ContextEngine）的工作不是“尽量多塞上下文”，而是在有限窗口里选择当前最该让模型看见的事实。

它要处理的来源包括：

```text
最新用户目标
工具结果
读取过的文件
项目规则
计划状态
验证状态
最新失败
长期记忆
压缩摘要
附件引用
仓库理解结果
批准或打断事件
子代理结果
```

它还必须处理预算压力：

```text
长命令输出不能一直原样塞进上下文；
旧成功日志通常不如最新失败重要；
活跃计划、验证状态、最新失败是硬状态；
可重新获取的大内容应该变成附件引用；
长期记忆不能和压缩摘要混成一团。
```

Lab 05 证明了最小上下文引擎：硬状态在预算压力下保留，长输出转附件，低相关记忆被排除，最新失败能在极小预算下保留。

Core 03 把它接入核心运行时。Core 18 再把它升级为上下文经济（Context Economy）：

```text
稳定前缀（stable prefix）
动态尾部（dynamic tail）
词元驱逐（token eviction）
附件边界（artifact boundary）
缓存模拟（cache simulation）
非纯提示词节省（no prompt-only saving）
```

Core 25 又加入仓库理解（Repo Intelligence）：

```text
仓库地图（repo map）
符号索引（symbol index）
测试索引（test index）
规则发现（rule discovery）
相关性评分（relevance scoring）
增量更新（incremental update）
词元收益证据（token benefit evidence）
```

这时上下文引擎解决的不只是“上下文太长怎么办”，而是：

```text
本轮模型为什么看见这些文件、这些测试、这些规则，而不是另一些？
被排除的信息是否可解释？
被选择的信息是否节省词元并提高命中率？
```

上下文层如果做不好，会出现三种失败：

```text
缺事实：模型凭空改。
挤事实：长日志挤掉关键失败。
混事实：记忆、压缩、仓库事实、工具结果权威层级混乱。
```

所以，上下文引擎是智能体的认知边界，不是提示词拼接器。

## 9. 计划状态：计划不是文本，而是运行时控制结构

计划模式（Plan Mode）容易被误解成“先让模型列个计划”。但课程已经把它讲清楚：计划不是一段漂亮文本，而是会改变权限和执行路径的运行时状态。

Lab 06 先证明：

```text
计划模式中可以读取；
编辑在批准前被拒绝；
模糊计划不能通过验证；
批准后的计划会成为活跃执行上下文。
```

Core 04 把它接进主运行时，Core 20 再把它升级为计划状态机（Plan State Machine）：

```text
步骤生命周期（step lifecycle）：待处理 -> 活跃 -> 完成
阻塞原因（blocked reason）
修订历史（revision history）
压缩后恢复（resume after compaction）
权限绑定到活跃步骤（permission bounded to active step）
最终回答依据（final grounding）
畸形计划拒绝（malformed plan rejection）
```

计划开始具有可恢复性和可审计性。它不再只是：

```text
1. 看文件
2. 改代码
3. 跑测试
```

而是带有：

```text
计划编号
步骤列表
活跃步骤
步骤状态
阻塞原因
预期文件
风险
验证方式
修订历史
恢复轨迹
批准状态
```

这样做的意义是：当任务变长、失败变多、上下文压缩发生、用户中途改需求时，系统还能知道自己原本在做哪一步、这一步为什么卡住、用户改了什么约束、哪些步骤已经完成、下一步是否仍然允许写。

所以计划状态的本质是控制结构，不是表达结构。

## 10. 压缩：压缩不是摘要，而是任务状态保真

长任务一定会遇到上下文窗口压力。低质量实现会把压缩当成“总结聊天记录”。这会导致最危险的问题：

```text
目标漂移
约束丢失
失败被写成成功
活跃计划断片
修改文件原因丢失
下一步动作消失
```

Lab 07 证明最小压缩：

```text
目标保留（objective preserved）
最新用户约束保留（latest user constraints preserved）
活跃计划保留（active plan preserved）
修改文件保留（modified files preserved）
失败验证不能写成通过（failed verification not marked passed）
长输出附件化（long output artifacted）
新消息不被旧摘要覆盖（newer messages not overwritten）
待处理动作保留（pending actions preserved）
```

Core 05 把压缩接入运行时。Core 19 又做了压缩质量评测（Compaction Quality Eval），让压缩质量可以机器检查：

```text
目标保真
约束保真
失败保真
计划保真
修改文件保真
待处理动作保真
压缩损失归因（compaction_loss attribution）
```

对代码智能体来说，压缩不只是节省词元，而是维护连续性的手术。好的压缩不是把一切写短，而是保住这些硬状态：

```text
目标
约束
最新失败
活跃计划
修改文件
验证状态
待办动作
附件引用
```

这也是为什么 Core 18 的上下文经济和 Core 19 的压缩质量必须连续出现：先解决“哪些内容该进上下文”，再解决“压缩后任务现实有没有失真”。

## 11. 评测证据：没有验证，智能体只是看起来会工作

代码智能体最容易自欺的地方是：它看起来完成了任务。

模型会写出自信的最终回答，甚至会解释自己做了什么。但如果没有验证状态，这些都只是叙述，不是证据。

Lab 08 建了最小评测运行器（Eval Runner）：

```text
评测用例
通过 / 失败分数
失败类型
用例模式
命令失败归因
```

Core 06 把追踪与评测框架（Trace / Eval Harness）接进核心链路：

```text
运行时追踪
上下文快照
工具序列证据
缺少验证归因（verification_missing）
策略回归证据
```

Core 10 到 Core 17 又把能力证明继续推进：

```text
入门评测打包（starter eval packaging）
20/20 可执行仓库种子（executable repo seeds）
参考智能体运行记录（reference-agent run record）
词元 / 缓存 / 延迟 / 哈希成本口径
本地配置美元估算（configured estimated USD）
定价边界（pricing boundary）
相对分数在第二基线前阻塞（RelativeScore blocked until second baseline）
```

这条链最重要的贡献是把“能力”拆成不同证据层级：

```text
本地确定性验证通过；
可执行种子通过；
参考智能体样本运行存在；
成本口径可计算；
定价表是本地配置；
真实厂商账单没有证明；
真实 Claude Code 基线没有证明；
相对分数没有第二智能体基线前不能声明。
```

公开学习项目必须守住这条边界：可以证明自己的机制跑通，但不能把本地证据夸大成生产级能力。

---

## 12. 真实仓库层：从玩具工作区到工程环境

一个智能体在玩具工作区中能跑，不代表它能处理真实仓库。真实仓库多了很多约束：

```text
版本状态
项目规则
包脚本
多个相似文件
测试入口
过期编辑
公开接口边界
项目自己的命名和目录习惯
```

Core 09 把任务推进到真实仓库夹具（real repo fixture），证明智能体不只是能在玩具文件里替换字符串，而是能：

```text
先观察版本状态；
读取项目规则；
发现测试命令；
多文件搜索；
从过期编辑中恢复；
保持公开接口；
最终基于测试回答。
```

Core 11 到 Core 14 把入门用例逐批变成可执行仓库种子，避免评测停留在纸面用例。

Core 25 的仓库理解进一步说明：真实仓库不是“把所有文件扔给模型”，而是要建立可解释索引：

```text
哪个源码文件相关；
哪个测试文件相关；
哪个包脚本应该跑；
哪个项目规则优先；
为什么这些文件被选中；
节省了多少词元。
```

这就是代码智能体在真实工程里站稳的关键：

```text
不是让模型读更多，而是让运行时更会选择、解释和验证。
```

## 13. 生产化升级：闭环越强，治理越是核心结构

当最小运行时能跑之后，下一阶段不是继续堆功能，而是处理生产化压力。

Core 18-26 解决的是“能跑之后最容易失控的九个边界”：

| Core | 主题 | 解决的问题 |
| --- | --- | --- |
| Core 18 | 上下文经济（Context Economy） | 预算、缓存、驱逐和附件边界 |
| Core 19 | 压缩质量（Compaction Quality） | 压缩前后状态保真 |
| Core 20 | 计划状态机（Plan State Machine） | 步骤生命周期、阻塞、修订和恢复 |
| Core 21 | 长任务评测（Long-Running Task Eval） | 多轮失败、压缩恢复、成本曲线、禁止假完成 |
| Core 22 | 工具运行时事务（ToolRuntime Transaction） | 差异预览、提交、回滚、高风险动作 |
| Core 23 | 模型网关预算（ModelGateway Budget） | 词元 / 成本闸门、重试、降级、能力过滤 |
| Core 24 | 持久会话回放（Durable Session Replay） | 追加式事件日志、快照、崩溃恢复、追踪回放 |
| Core 25 | 仓库理解（Repo Intelligence） | 仓库地图、符号 / 测试 / 规则索引、相关性评分 |
| Core 26 | 人工批准（Human Approval） | 批准、拒绝、打断、交接、禁止隐藏执行 |

这些机制共同回答一个问题：

```text
当智能体不再只是跑三步，而是持续推进真实任务时，怎么让它仍然可控？
```

答案不是“让模型更小心”，而是把治理写进运行时：

```text
预算在模型服务商调用前检查；
写入在事务里提交；
高风险动作进入批准；
用户打断变成会话事件；
崩溃后从快照和事件日志恢复；
压缩能被质量评测识别损失；
最终回答必须避开假完成。
```

这也是早期文章里“治理不是外围模块，而是核心结构”的实现版本。

## 14. 产品表层：把产品名称转译成运行时边界

课程后半段最有价值的一点，是没有把设置、钩子、记忆、检查点、子代理当成功能清单，而是逐个问：

```text
它是否新增运行时状态？
它是否新增强制边界？
它是否有最小夹具？
它是否有验证用例？
它是否不重复已有 Core？
它是否能守住公开边界？
```

Core 27-31 就是这套筛选之后的五个产品表层 Core：

| Core | 主题 | 运行时化之后真正证明什么 |
| --- | --- | --- |
| Core 27 | 设置与权限解析器（Settings / Permission Resolver） | 配置规则在工具执行前解析为允许、询问、拒绝，并记录规则来源、解析轨迹和决策缓存 |
| Core 28 | 钩子生命周期（Hooks Lifecycle） | 用户提示、工具前、工具后钩子是运行时生命周期事件，可以阻断、补充观察、添加约束、脱敏，而不是升级成系统提示词 |
| Core 29 | 记忆来源 / 项目记忆 / 自动记忆（Memory Source / CLAUDE.md / Auto Memory） | 长期记忆是可路由、可索引、可删除、可重新验证的上下文来源，不是压缩，也不是仓库理解 |
| Core 30 | 检查点与回退（Checkpoint / Rewind） | 用户可见恢复点绑定文件哈希、会话事件、外部改动冲突和审计回放 |
| Core 31 | 子代理上下文隔离（Subagent Context Isolation） | 委派任务拿隔离上下文，返回摘要、证据和结构化失败，并由账本阻止重复研究 |

这一步补上了一个非常重要的学习能力：

```text
看到产品表层，不急着复刻界面，也不急着复制材料。
先判断它是否能被转译成自己的对象模型、状态、边界和验证。
```

这就是公开学习边界的核心：学习机制，不复制私有实现。

## 15. 三个核心场景

### 15.1 代码修改

低质量实现会让模型直接输出补丁。成熟的代码智能体会这样走：

```text
读项目规则
搜索候选文件
读取目标文件
确认公开接口和调用关系
形成计划或活跃步骤
检查权限
生成差异预览
执行编辑
记录修改文件
运行测试
根据失败继续修
验证通过后最终回答
```

代码修改不是“生成代码”，而是受约束的对象关系修正。

### 15.2 测试

测试不是最后打分器，而是认知探针。

一次命令失败会更新：

```text
验证状态
最新失败
活跃计划
待处理动作
评测证据
```

下一轮模型不是“再试一次”，而是基于失败事实收缩问题空间：

```text
哪个断言失败；
哪个文件可能相关；
之前假设哪里错了；
下一步应该读、改、问人还是重规划。
```

所以测试输出必须被结构化和裁剪，长输出转附件，关键失败保留为硬状态。

### 15.3 调试

调试不是“模型更聪明地猜问题”，而是一个归因树逐步收缩过程：

```text
观察失败
定位相关文件
形成假设
读取证据
修改最小片段
验证
若失败，保留失败并修正假设
若上下文压力升高，压缩但保留目标 / 约束 / 失败 / 计划
若外部改动冲突，停止覆盖
若风险升高，请求人类批准
```

这正是为什么消息流、上下文引擎、计划状态、压缩、工具运行时事务和评测证据必须一起存在。

## 16. 从零搭建的推荐顺序

如果现在重新从零实现一个代码智能体，不应该从复杂多智能体或华丽界面开始。推荐顺序是：

### 第一阶段：最小闭环

```text
会话
消息流
搜索 / 读取 / 命令执行
工具结果回灌
最终回答依据
```

目标：证明模型、工具和状态能形成循环。

### 第二阶段：安全编辑

```text
编辑
先读再写
旧字符串唯一
文件过期检查
路径安全
命令白名单
```

目标：让智能体可以改变工作区，但不能乱改。

### 第三阶段：模型边界

```text
模型网关
模型服务商适配器
工具模式校验
输出归一化
模型服务商失败归一化
```

目标：模型可替换，运行时不被模型服务商形状绑死。

### 第四阶段：上下文和长任务

```text
上下文引擎
附件边界
计划状态
压缩
活跃计划 / 最新失败 / 验证状态硬保留
```

目标：任务变长后仍然不断片。

### 第五阶段：证据和真实仓库

```text
追踪
评测框架
真实仓库夹具
可执行种子
失败归因
```

目标：把“能跑”变成“可证明”。

### 第六阶段：生产化边界

```text
上下文经济
压缩质量
长任务评测
工具运行时事务
模型网关预算
持久回放
仓库理解
人工批准
```

目标：把长任务、成本、恢复、权限和协作压力变成可治理对象。

### 第七阶段：产品表层机制

```text
设置与权限解析器
钩子生命周期
记忆来源
检查点与回退
子代理上下文隔离
```

目标：把产品表层能力转译成运行时状态、强制边界和验证证据。

这七阶段合起来，就是本项目课程、实验、核心阶段的搭建过程。

## 17. 最终架构图

用一条完整链路表示：

```text
用户
  -> 会话控制器
  -> 消息流追加用户消息
  -> 上下文引擎构造本轮可见事实：
       最新用户目标
       项目规则
       工具结果
       已读取文件
       活跃计划
       验证状态
       压缩摘要
       记忆
       仓库理解
       批准事件
       附件引用
  -> 模型网关调用模型：
       上下文
       可用工具模式
       预算和能力闸门
  -> 模型决策：
       最终回答或工具调用
  -> 权限解析器：
       允许、询问或拒绝
  -> 钩子生命周期：
       用户提示、工具前、工具后
  -> 工具运行时：
       搜索 / 读取 / 编辑 / 命令 / 事务
  -> 观察：
       工具结果 / 策略拒绝 / 钩子反馈 / 验证结果
  -> 状态存储更新：
       修改文件
       验证状态
       最新失败
       计划状态
       会话事件
       记忆事件
       检查点事件
       委派事件
  -> 评测证据抽取
  -> 继续 / 压缩 / 重规划 / 批准 / 回退 / 委派 / 最终回答
```

这个图里没有任何一步可以完全交给模型自觉完成。

模型负责判断和生成候选动作；运行时负责让动作成为受控事实。

## 18. 为什么它更像软件任务操作系统

一个代码智能体运行时像操作系统，不是因为它有界面或命令行，而是因为它管理这些东西：

```text
任务：会话、计划、子代理委派任务
资源：上下文窗口、词元预算、文件、命令、记忆
权限：允许、询问、拒绝、批准、策略优先级
执行：工具执行、长任务评测、打断、恢复
文件状态：读取快照、过期检查、事务、检查点、回退
日志：追加式事件日志、追踪、回放、审计
调度：可并行安全工具、重复研究账本、模型服务商降级
恢复：压缩、快照、崩溃恢复、交接
观测：评测证据、失败归因、成本曲线
```

它不是传统操作系统，但它承担了“让软件任务在不确定环境里可控运行”的那部分职责。

所以真正的代码智能体不是“带工具的聊天机器人”，而是：

```text
一个把模型推理接入工程环境，并用状态、权限、工具、上下文和验证约束它的任务运行时。
```

## 19. 有效性边界

这套实现逻辑已经能解释并证明很多代码智能体核心机制，但它不能声称：

```text
这是 Claude Code 官方实现；
这是 Claude Code 源码复刻；
它可以替代 Claude Code 生产使用；
它证明真实大仓库 70%-80% 成功率；
它拥有真实 Claude Code 基线；
它拥有真实模型服务商账单证据；
它拥有跨智能体相对分数；
它实现了真实远端 worker 隔离或智能体 marketplace。
```

它能声称的是：

```text
本项目用自己的代码和验证脚本，复现并验证了一个代码智能体运行时的核心搭建路径：
从最小循环，到工具安全，到模型边界，到上下文和计划，到评测证据，到生产化治理，再到产品表层机制的运行时化。
```

这已经足够形成一套可复刻的学习框架。

## 20. 最终判断

如果要完整回答“代码智能体到底怎么实现”，答案不是：

```text
写一个强提示词；
接一个强模型；
给它几个工具；
让它自动循环。
```

真正的答案是：

```text
先把代码任务建模成会话；
把所有事实写进消息流；
用上下文引擎决定模型每轮可见世界；
用模型网关固定模型边界；
用工具运行时执行真实动作；
用权限、策略和钩子阻止隐藏执行和越权；
用计划状态管理长任务步骤；
用压缩和持久回放保持连续性；
用仓库理解提高真实仓库相关性；
用人工批准管理高风险协作节点；
用记忆、检查点、子代理隔离承载产品表层能力；
最后用评测证据证明每一步到底成立了什么。
```

这就是从“模型会写代码”到“代码智能体可以持续推进软件任务”的工程跨越。

也正是本项目完整课程真正搭出来的东西。
