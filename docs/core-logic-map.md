# Claude Code-like Agent 核心逻辑总览

本文是第一次理解本项目时的机制地图。它不以代码为主角，也不要求你先读源码；它先回答：

```text
一个 Claude Code-like 代码智能体，为什么能从用户目标一路走到工具执行、状态更新、验证和产品体验？
```

代码、Core 文档和验证脚本（verify scripts）是证据入口。先把逻辑链路看懂，再去看它们如何被本项目实现和证明。

---

## 1. 一句话主线

Claude Code-like Agent 不是“一个会聊天的模型加几个工具”。它更像一个受控运行时（Runtime）：

```text
User Goal
  -> Runtime Loop
  -> Context
  -> Model Decision
  -> Tool Call
  -> Policy
  -> ToolRuntime
  -> Observation
  -> State
  -> Plan
  -> Compaction
  -> Eval
  -> Product Surface
```

这条链路里，模型只负责在当前上下文里做决策；真正读文件、改文件、跑命令、记录事实、控制权限、压缩历史和验证结果的，是运行时。

## 3. 每个环节负责什么

| 环节 | 中文理解 | 它解决的问题 |
| --- | --- | --- |
| User Goal | 用户目标 | 用户并不是给模型一段孤立聊天，而是交给系统一个需要持续推进、可能要改代码和验证的任务。 |
| Runtime Loop | 运行时循环 | Agent 必须一轮一轮推进：组装上下文、请求模型、执行工具、接收结果、更新状态，再进入下一轮。 |
| Context | 上下文 | 模型本轮能看见什么，必须由上下文引擎组织；模型不能凭空知道文件、历史、规则或工具结果。 |
| Model Decision | 模型决策 | 模型根据本轮上下文选择下一步：回答、请求工具、更新计划、等待用户或结束。 |
| Tool Call | 工具调用 | 模型只能提出工具意图和参数，不能自己直接读写文件或执行命令。 |
| Policy | 策略 / 权限 | 每个工具意图都要经过规则判断：允许、拒绝、需要确认，或要求先补上下文。 |
| ToolRuntime | 工具运行时 | 真正执行读文件、搜索、命令、编辑和事务的地方；它负责把副作用变成可审计事件。 |
| Observation | 观察结果 | 工具结果必须回灌给运行时和模型，成为下一轮上下文里的事实，而不是散落在终端输出里。 |
| State | 状态 | 任务进度、文件变化、失败原因、批准结果、成本和会话事件都要进入状态，才能恢复和复盘。 |
| Plan | 计划 | 计划不是模型写的一段漂亮文本，而是可更新、可阻塞、可恢复、可落地到最终回答的状态机。 |
| Compaction | 压缩 | 长任务不能无限堆历史；压缩要保留目标、约束、失败、计划和关键证据，而不是普通摘要。 |
| Eval | 评测 | “看起来修好了”不够；必须用可运行验证、失败归因和边界说明证明能力是否成立。 |
| Product Surface | 产品表层 | 设置、权限、钩子、记忆、检查点和子代理这些用户可见能力，最终都要落成运行时状态和强制边界。 |

## 4. 为什么不要一开始读代码

第一次学习时，直接从 `src/core/` 读起会很容易迷路。因为代码里同时出现了模型网关、上下文、工具、计划、压缩、评测、会话、仓库理解和产品表层机制。

更稳的顺序是：

```text
先理解机制链路
再看每个机制解决什么问题
再用 Course / Lab / Core 深入
最后用 verify 证据确认行为
```

也就是说，代码不是主路径的起点，而是你验证理解时进入的证据层。

---

## 5. Course / Lab / Core 应该怎么放回地图里

本项目仍然保留 `course -> lab -> core` 命名系统，但它们是深入学习材料，不是首页第一理解负担。

| 层级 | 作用 | 什么时候看 |
| --- | --- | --- |
| Course | 解释机制为什么存在，以及如何避免越界声称 | 你已经知道完整链路，想按学习路线逐段理解时 |
| Lab | 拆开单个机制，用最小实验看它如何跑起来 | 你想单独理解消息流、工具、上下文、计划、压缩或评测时 |
| Core | 把机制集成成可运行核心，并记录每阶段证明了什么 | 你想知道本项目当前实现到哪里、哪些行为被验证时 |
| Verify | 机器可运行证据 | 你要确认某个机制真的成立，或检查文档声明有没有证据时 |

这也是 README、学习者入口和学习计划采用的新顺序：先看逻辑总览，再进入学习路线和证据。

## 6. 一次任务如何跑完

可以把一次任务理解成下面这段循环：

```text
1. 用户给出目标和约束。
2. 运行时创建或恢复会话状态。
3. 上下文引擎选择本轮模型能看到的材料。
4. 模型做出下一步决策。
5. 如果模型请求工具，运行时先经过 Policy 判断。
6. ToolRuntime 执行允许的工具，并把结果包装成 Observation。
7. Observation 进入 State，Plan 也随之更新。
8. 如果历史太长，Compaction 保留关键任务状态。
9. Eval 或 verify 证明结果是否真的成立。
10. Product Surface 把这些边界呈现为用户能理解和控制的体验。
```

这里最重要的分工是：

```text
模型提出意图；
运行时执行和约束；
工具结果成为事实；
状态保证恢复；
评测约束能力声明。
```
